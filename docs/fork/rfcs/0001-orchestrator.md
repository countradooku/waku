# RFC 0001: `waku-orchestrator`, an event-sourced daemon core

- **Status:** Accepted (pending merge of Phase 0 PR). Tracked in [#11](https://github.com/countradooku/waku/issues/11).
- **Implements:** Phase 2 ([#165](https://github.com/countradooku/waku/issues/165)): [#39](https://github.com/countradooku/waku/issues/39), [#40](https://github.com/countradooku/waku/issues/40), [#41](https://github.com/countradooku/waku/issues/41), [#42](https://github.com/countradooku/waku/issues/42), [#43](https://github.com/countradooku/waku/issues/43), [#55](https://github.com/countradooku/waku/issues/55), [#59](https://github.com/countradooku/waku/issues/59), [#63](https://github.com/countradooku/waku/issues/63), [#64](https://github.com/countradooku/waku/issues/64), [#65](https://github.com/countradooku/waku/issues/65). Shares types with [#44](https://github.com/countradooku/waku/issues/44) (RFC 0002) and [#54](https://github.com/countradooku/waku/issues/54), [#56](https://github.com/countradooku/waku/issues/56), [#57](https://github.com/countradooku/waku/issues/57) (RFC 0003).
- **Reference:** T3 Code orchestration v2 at the pinned snapshot ([audit](../audit/t3-server.md) §1, `t3code/packages/contracts/src/orchestrationV2.ts`, `t3code/apps/server/src/orchestration-v2/`, `t3code/docs/orchestration-v2/`).

## Problem

Today the desktop builds the transcript and the daemon does not.

- The daemon forwards provider events and persists whatever the desktop sends back in `SaveTaskState`.
- With no client attached, a running turn is only kept in a 2,048-event in-memory journal.
- Saves are full-session snapshots sent from the UI thread.

This rules out background agents, scheduled tasks, a consistent view across several clients, and reliable crash recovery.

## Goals

- The daemon is the only source of truth for projects, threads, runs and transcripts.
- Every user or agent intent is durable before any side effect runs.
- Side effects survive restarts with explicit "replay safe" vs "process bound" semantics.
- Clients receive bounded snapshots plus small replays, never whole transcripts.
- Feature behaviour follows provider capabilities, not provider names.

## Non-goals

- Wire compatibility with T3 Code. Decision D1: we speak our own protocol (RFC 0003).
- Storing raw provider frames in SQLite. They go to rotating diagnostic logs.
- Designing Phase 3+ behaviour (queue editing UI, forks, handoffs, delegated tasks, PR watch, workflows). The types and tables below already have room for them so Phase 3 adds behaviour, not schema. Commands marked **(P3)** are defined now and return `CommandError::Unsupported` until then.

## Decisions

The three open questions of the draft are R1–R3. The rest were settled while writing the type and schema sketches.

| # | Decision | Rationale |
|---|---|---|
| R1 | `payload_json` is plain JSON text (`serde_json`), not postcard and not zstd-compressed. | It stays inspectable with `sqlite3` and `json_extract`, SQL migrations can rewrite payloads, and large bodies are already capped in storage (R12, [#57](https://github.com/countradooku/waku/issues/57)), so compression would save little. |
| R2 | One daemon-wide database file, `state.sqlite`. | Forks, delegated tasks and provider sessions span threads and projects; one file keeps every cross-thread write inside one transaction. |
| R3 | Keep every event in Phase 2. Later, compact only by superseding: for runs terminal for more than 30 days, delete all but the last `*.updated` event per entity. Settled effects are pruned after 7 days (batches of 500), failed effects are kept, receipts are pruned after 30 days. | Events are full snapshots, so dropping superseded ones keeps "rebuild = live" true, and any cursor that old gets a fresh snapshot anyway. |
| R4 | `state.sqlite` is a new file next to `app.db`. `app.db` becomes a read-only import source and is never written once [#55](https://github.com/countradooku/waku/issues/55) lands. | A failed migration can never damage the old data, and import can run again from the original file. |
| R5 | Fork migrations are hand-written SQL in `crates/waku-orchestrator/migrations/`, embedded by that crate's `build.rs` and recorded in their own ledger table, `orchestrator_migrations`. They are not generated by drizzle. | FTS5 virtual tables, partial indexes, `STRICT` tables and `CHECK`s are outside drizzle's schema DSL. Rust owns every query anyway, and a separate directory and ledger mean upstream's `db/migrations` can never collide. |
| R6 | App ids are UUID newtypes. New ids are UUIDv7; ids derived from stable inputs are UUIDv5; imported Waku ids (v4) are kept as they are. `CommandId` is a string of 1–256 bytes. | v7 sorts by time in indexes, v5 makes retries idempotent, keeping the old ids makes the import idempotent, and derived command ids (`limit-resume:<thread>:<run>:<reset>`) must be readable. |
| R7 | Timestamps are `i64` unix milliseconds UTC, stored as `INTEGER`. | Cheap to index and compare. Waku's seconds are multiplied by 1,000 on import. |
| R8 | Projects are event-sourced too. The lock key is `Thread(ThreadId)` or `Project(ProjectId)`. | `SaveTaskState` also carries projects today; retiring it ([#55](https://github.com/countradooku/waku/issues/55)) needs project commands, and the shell stream needs project events. |
| R9 | `waku-orchestrator` exposes blocking APIs and has no async runtime dependency. Drivers run on the daemon's tokio runtime (RFC 0002 decision 1). The port implementations in `waku-core` bridge the two: effect workers stay OS threads and talk to driver session actors through channels or `Handle::block_on`, and driver events reach the sink through a bounded channel drained by a blocking ingest thread. | `decide` is pure and the sink is one rusqlite connection, so neither benefits from async. Keeping the crate runtime-free lets it be tested without tokio while drivers get async I/O. |
| R10 | The orchestrator keeps an in-memory `ThreadProjection` per hot thread: the whole control graph plus messages and turn items of non-terminal runs. Up to 64 threads are cached (LRU) and the rest load from SQLite on demand. | `decide` needs the graph, not five thousand history rows. Streams and search read history from SQLite. |
| R11 | Each entity kind has exactly one event, `<entity>.updated`, carrying the full entity. Thread events also carry a `ThreadChange` reason. T3's separate `created`, `detached`, `rollback-requested` and `background-work-cancelled` events become fields on the entity. | One rule, "apply is an upsert by id", with no special cases. The reason keeps the audit trail. |
| R12 | Streaming text is persisted at block boundaries (a finished markdown line, T3's `splitBufferedAssistantText` rule) at most every 250 ms, and on every status change. Between persists, clients receive unsequenced `delta` stream items (RFC 0003 §5.4, applied by `streamRev`). Stored command output is capped at 256 KiB (head 64 KiB + tail 192 KiB); the full output lives only in the output hub. | Persisting every 16 ms delta as a full snapshot would grow the log quadratically with message length. |
| R13 | `RunStatus` adds `Finalizing`: the provider is done and the finalization barrier is running. `Waiting` keeps T3's meaning, waiting on the user. | T3 overloads `waiting` for both. Recovery and forking need to tell them apart. |
| R14 | A queued run has `ordinal = None` and a `queue_position`. It takes the next ordinal when it leaves the queue. | Ordinals then count exactly the runs the provider saw, which is what rollback counts. Reordering the queue never renumbers history. |
| R15 | `decide` assigns each turn item a `position` once, when it is created: `(run_ordinal << 24) \| n`, where `n` counts items in that run's block. Items outside a run use the block of the latest started run (block 0 before any run). There is no separate positions table. | Ordering is domain logic, so it stays in the pure function. The position doubles as the history-paging cursor and makes rebuild deterministic. |
| R16 | Rejected commands get a receipt too (`status = 'rejected'` plus the error). | Retrying a rejected command id returns the same error instead of re-deciding against newer state. |
| R17 | Types that cross the wire or reach disk (ids, entities, turn items, `DomainEvent`, client `Command`) live in `waku-protocol::orchestration`. Daemon-only types (`InternalCommand`, `Decision`, `Effect`) live in `waku-orchestrator`. | Clients and daemon share one definition, and RFC 0003 generates the TypeScript from it. |
| R18 | Import from the fork's own `app.db` is automatic. Import from upstream Waku's `app.db` only happens on an explicit user action and opens that file read-only. | D5 says the fork never touches upstream's files on its own; [#63](https://github.com/countradooku/waku/issues/63) still needs a path for upstream users. |
| R19 | Projection tables declare no foreign keys. `waku doctor` verifies references instead. | Snapshot events of different entity kinds can arrive in any order, and rebuild must accept them. |
| R20 | Tagged unions use serde's internally or adjacently tagged forms with `#[serde(other)] Unknown`. This needs a self-describing encoding. JSON satisfies it on disk and for web; RFC 0003 uses MessagePack (maps with named fields) for native frames, which does too. | Forward compatibility requires decoding unknown tags. |
| R21 | Effects report back as internal commands with derived ids `effect:<effect_id>:<n>`. | A replay-safe effect that re-runs after a crash re-dispatches the same ids, and the receipts turn those into no-ops. |
| R22 | `TurnItem` and `Plan` nest their variant under a `kind` field instead of flattening it into the base fields as T3 does. | We do not need T3's wire shape, and serde `flatten` with tagged enums is fragile under binary codecs and ts-rs. |
| R23 | Imported provider cursors become strong native thread refs, so imported threads resume natively. | T3 starts imported threads fresh with a 32k-character handoff; every Waku driver already resumes from these cursors. |
| R24 | Search uses FTS5 with `contentless_delete=1`, the `unicode61 remove_diacritics 2` tokenizer and prefix indexes 2 and 3. Snippets are built in Rust from the source row. | It meets [#65](https://github.com/countradooku/waku/issues/65)'s budget without storing text twice; a trigram index is about three times larger. |

## Pipeline

```
client request / MCP tool / scheduler / effect result          provider driver (RFC 0002)
  → CommandEnvelope (app ids only)                                → AdapterEvent
  → receipt lookup (duplicate → stored result)                    → IngestEnvelope
  → per-key lock (thread or project; creates also lock the new id)
  → decide(&mut DecideContext, &AnyCommand) -> Decision           decide_ingest(..) -> Decision + WriteGuard
        { events, effects, cancel_unsettled }                     // both: no I/O
  → EventSink::commit   // ONE SQLite transaction (BEGIN IMMEDIATE):
        check receipt again, check guard
        append events (global sequence)
        apply events to projection tables (upsert by entity id) and search docs
        write command receipt (command_id → last sequence)
        cancel unsettled effects
        enqueue outbox effects
  → after COMMIT: apply to the in-memory projection, publish to streams, wake effect workers
  → EffectWorkerPool (lease, per-thread FIFO, title lane) runs effects
  → results come back as InternalCommands or as AdapterEvents
```

### Rules

1. `decide` reads only its context (projection, clock value, id source, capability lookup) and the command. It is a plain function with no I/O and is unit-testable.
2. Dispatch returns the last committed sequence.
   - A duplicate `command_id` returns the stored receipt and emits nothing. A duplicate of a rejected command returns the stored error.
   - Command ids derived from stable inputs (MCP `clientRequestId`, `limit-resume:<thread>:<run>:<reset>`, `effect:<id>:<n>`) make retries idempotent.
3. A command holds only its own key's lock, plus the lock of any thread it creates (always sorted, so locks never deadlock). Cross-thread writes to existing threads (stopping child threads) go through post-commit effects. Reading another thread's projection read-only (a fork source) is allowed.
4. Events carry full entity snapshots: `RunUpdated(Run)`, `TurnItemUpdated(TurnItem)` and so on. Applying an event is an upsert by id, which keeps replay and client reducers trivial.
5. Provider ingestion commits only if its `WriteGuard` holds: the run attempt is still current, the provider thread is still owned by this thread, the provider thread is unchanged, or the native thread is not owned elsewhere. A failed guard drops the whole decision.

## Entity model

```
Project
  AppThread                       user-visible conversation; survives provider exits
    Run (ordinal)                 counted user-visible turn; only its root node completes it
      RunAttempt                  initial | steering_restart | retry | provider_recovery
        ExecutionNode tree        root_turn, assistant_message, reasoning, plan, todo_list,
                                  tool_call, approval_request, user_input_request, subagent, hook, system
    Subagent                      provider_native | app_owned; child_thread_id; completion delivery
    ProviderSession               live/resumable runtime + Capabilities (RFC 0002)
    ProviderThread                native conversation handle (ProviderRef{driver, native_id, strength})
      ProviderTurn                native turn + token usage
    RuntimeRequest                approval | user_input | dynamic_tool_call | auth_refresh
    Message                       user/assistant/system; attachments; context records
    Plan                          proposed_plan (markdown) | todo_list (steps)
    TurnItem (ordered)            the display projection (24 variants + Unknown)
    CheckpointScope / Checkpoint  hidden git refs; nested scopes do not advance the run count
    ContextTransfer / Handoff     fork | provider_handoff | merge_back | subagent_spawn | subagent_result
```

### Invariants (from T3 v2)

- App ids are primary. Provider ids are references with a strength: strong, weak or none.
- A child execution completing never closes the parent run.
- A run is terminal only after the provider's terminal event and the finalization barrier: flush streams, finalize plans, close child nodes, capture the checkpoint.
- Rollback is expressed in app run count and reconciled with the provider conversation.

## Rust types

Field names follow T3 v2 where the meaning is the same. All structs derive `Clone, Debug, Serialize, Deserialize, TS` and use `#[serde(rename_all = "camelCase")]`; all enums crossing the wire or disk add `#[serde(other)] Unknown` (R20). Optional fields use `#[serde(default, skip_serializing_if = ...)]`, so adding one later never needs a migration. "Deferred" lines name the T3 fields left out until the phase that needs them.

- These are T3's 24 variants. [#43](https://github.com/countradooku/waku/issues/43) counts 26 because it lists background tasks and delegated tasks separately; as in T3, those are `Notification` items (`NotificationSource::{BackgroundTask, Command, Monitor, Subagent, DelegatedTask, System, Unknown}`) and `Subagent` items, not separate variants.

`dispatch` does, in order: validate; look up the receipt on a read connection (a hit returns at once); take the lock keys; load the projections from the cache or SQLite; read `now`; `decide`; `EventSink::commit` (or `commit_rejection`); `apply` to the cached projection, or drop the cache entry if the commit failed; release the locks; call the effect waker.

The transaction runs `BEGIN IMMEDIATE` and then: (1) recheck the receipt; (2) check the guard against projection rows; (3) insert the events; (4) `apply_sql` each event (projection upsert, derived columns, search docs); (5) insert the receipt with the last sequence, or with the current maximum when there are no events; (6) cancel unsettled effects (`UPDATE … SET status = 'cancelled'` for matching pending and running rows); (7) insert the outbox rows; `COMMIT`. Publishing happens only after `COMMIT` returns.

A worker loop: claim (SQL below) → re-read the row and exit if it is now `cancelled` → run `execute` raced against the effect's `CancelToken` → settle as `succeeded`, retry (`pending`, `available_at = now + min(cap, base · 2^(attempt-1))`), or `failed` after `max_attempts` or on `Permanent`. A settle only succeeds while the worker still holds the lease (`WHERE lease_owner = ?`).

The built-in executor is `DefaultExecutor { sessions: Arc<ProviderSessionManager>, ports: Ports }`. It handles the `provider_*` and `runtime_request.*` effects through the session manager (RFC 0002, [#44](https://github.com/countradooku/waku/issues/44)) and the rest through ports, which `waku-core` implements:


Every port method is idempotent: preparing an existing worktree returns it, capturing an existing ref returns it. That is what makes the `requeue` effects below safe.

## Storage

### File, connections and pragmas

- **File:** `state.sqlite` in the daemon data directory (`identity::DATA_DIRECTORY_NAME`, "Waku Fork" per D5). Debug builds use `temp/state.sqlite` in the checkout, like `app.db` today.
- **Connections:** one writer connection owned by `Store` behind a mutex, shared by `EventSink` and the outbox (claims and settles are small writes; one writer means no `SQLITE_BUSY` between them). A pool of four `SQLITE_OPEN_READ_ONLY` connections serves streams, history, search and receipt lookups.
- **Pragmas** on every connection: `journal_mode=WAL`, `synchronous=NORMAL`, `busy_timeout=5000`, `foreign_keys=ON`, `journal_size_limit=67108864`, and `checkpoint_fullfsync=ON` on macOS. `auto_vacuum=INCREMENTAL` is set when the file is created, before the first table. Maintenance runs `PRAGMA incremental_vacuum(2048)` after pruning.
- **Table pattern:** indexed scalar columns plus `payload_json`, the entity's JSON (R1). Every table is `STRICT`. Ids are `TEXT`, timestamps and booleans are `INTEGER`.

### Migrations (R5)

- Files: `crates/waku-orchestrator/migrations/NNNN_name.sql`, starting at `0001_init.sql`. `crates/waku-orchestrator/build.rs` embeds them as `MIGRATIONS: &[(u32, &str, &str)]` (version, name, SQL), using the same rules as `waku-core/build.rs`: the numeric prefix is the order, gaps fail the build, empty files fail the build.
- Ledger, in `state.sqlite` only:

```sql
CREATE TABLE IF NOT EXISTS orchestrator_migrations (
  version    INTEGER PRIMARY KEY,
  name       TEXT    NOT NULL,
  checksum   TEXT    NOT NULL,   -- hex SHA-256 of the SQL text
  applied_at INTEGER NOT NULL
) STRICT;
```

- Each pending migration runs in its own transaction and inserts its ledger row in that transaction.
- `Orchestrator::open` refuses to start if a recorded checksum differs from the embedded SQL (an edited migration) or if the ledger holds a version the binary does not know (a downgrade). The error names the file and the version.
- Upstream's `migrations` table in `app.db` is never read or written by this code. `db/schema.ts` and `db/migrations/` are frozen and only describe what the importer reads.

Claiming one effect (per-lane FIFO; an earlier effect waiting out its backoff still blocks later ones, as in T3):

```sql
UPDATE effect_outbox
SET status = 'running', lease_owner = :worker, lease_expires_at = :now + :lease_ms,
    attempt_count = attempt_count + 1, updated_at = :now
WHERE effect_id = (
  SELECT c.effect_id FROM effect_outbox AS c
  WHERE c.status = 'pending' AND c.available_at <= :now
    AND NOT EXISTS (
      SELECT 1 FROM effect_outbox AS a
      WHERE a.lane_key = c.lane_key AND a.lane = c.lane
        AND (a.status = 'running' OR (a.status = 'pending' AND a.effect_id < c.effect_id)))
  ORDER BY c.effect_id LIMIT 1)
RETURNING *;
```

The liveness poll returns expired leases to `pending` (`WHERE status = 'running' AND lease_expires_at < :now`).

### DDL: search (`0002_search.sql`, [#65](https://github.com/countradooku/waku/issues/65))

```sql
CREATE TABLE search_docs (
  doc_id INTEGER PRIMARY KEY,          -- = search_fts rowid
  entity_kind TEXT NOT NULL CHECK (entity_kind IN ('message', 'plan', 'thread_title')),
```

`apply_sql` indexes messages once they stop streaming, plans on every update, and thread titles. It deletes the old row and inserts the new one in the same transaction. Search results return `(entity_kind, entity_id, thread_id, position)`, and snippets are cut in Rust from `p_messages` or `p_plans`, as `build_session_search_snippet` does today. `contentless_delete` needs SQLite 3.43 or later; the bundled rusqlite build is newer.

Workers:
- Use a lease-based claim (SQL above). An effect is claimable only if no earlier pending or running effect exists in the same lane of the same thread. The title lane only blocks other title effects, so title generation never delays a turn.
- Retry with exponential backoff (100 ms doubling, 30 s cap, 5 attempts). A provider-control error that the driver marks non-retryable settles as `succeeded`, as in T3.
- Cancel by thread and effect type through `Decision::cancel_unsettled`, which races an in-process `CancelToken` against execution. Re-read the row after claiming it.
- Prune settled rows after retention and keep failed rows.

## Streaming text and command output

- The `ProviderSessionManager` ([#44](https://github.com/countradooku/waku/issues/44)) owns a `StreamingCoalescer` per streaming item. It forwards text to thread streams as unsequenced `delta { itemId, channel, rev, text }` items (RFC 0003 §5.4; each persisted snapshot carries `streamRev`), coalesced over 8–16 ms, and turns the text into a persisted `TurnItemUpdated` (via `ingest`) at block boundaries, at most every 250 ms, and on every status change (R12). A client drops its `delta` buffer for an item when a sequenced snapshot of that item arrives. **RFC 0003 adds `delta` to the thread stream items.**
- `CommandOutputDelta` goes straight to the output hub ([#56](https://github.com/countradooku/waku/issues/56)) and never reaches `ingest`. The hub's tail is written into the item's `output` (capped) when the command completes.

## Recovery ([#59](https://github.com/countradooku/waku/issues/59))

On start, before the effect workers and the socket accept work, the daemon runs:

1. **`EffectWorkerPool::reconcile_after_process_loss`.** Pending and running process-bound effects become `cancelled` (`cancel_reason = 'process_loss'`). Running replay-safe effects go back to `pending`.
2. **Session cleanup.** Every `ProviderSession` not `stopped` is marked `stopped` with `detach_reason = "process_loss"`. Pending runtime requests with a `Live` response capability become `expired`, unless the session's capabilities say pending requests survive a restart (`sessions.pending_requests_survive_restart`), in which case they stay pending until the driver re-attaches.
3. **Candidate selection** from the projection (`p_runs_open`, `p_runtime_requests_pending`, `p_subagents`, `p_provider_threads.pending_background_tasks`): runs in `starting` or `running`, threads with queued runs and no active run, and undelivered subagent completions.
4. **Per thread**, `dispatch_internal` with `RecoverThread { thread_id, boot_id }` and command id `recover:<thread>:<boot_id>`. Its decision:
   - The interrupted attempt becomes `interrupted` and the run `interrupted`, with `failure = { class: TransportError, code: "process_loss" }`, plus a `SystemNotice` turn item ("Waku restarted while this turn was running").
   - If continuation is allowed, it enqueues `provider_runtime.continue { source_run_id, chain_length }`. Executing that effect dispatches `ContinueRun` (command id `restart-continue:<thread>:<run>`), which creates a new run with `continuation = { kind: Restart, of_run_id }`, a system-authored user message "Continue where you left off.", and the visible "resumed" row that [#59](https://github.com/countradooku/waku/issues/59) asks for.
   - Runs in `finalizing` need nothing: their `checkpoint.capture` was requeued in step 1.
   - Threads with queued runs and no active run start the head of the queue unless it is held.

Continuation is refused when: `continue_after_restart` is off; the thread is archived, deleted, settled or snoozed; the run was `waiting` on the user; newer user work is queued (the queue is released instead); the run was a `/compact` turn; or the chain already has `max_restart_continuations` (3) consecutive `Restart` continuations.

Graceful shutdown stops claiming, waits up to 5 s for running effects, then closes providers. The next start treats it like a crash, so there is only one recovery path.

## Streams (detailed in RFC 0003)

| Stream | Behaviour |
|---|---|
| Shell | Active navigation rows only (`p_threads_shell`, `p_threads_pinned`); deltas after a cursor. Archived rows come from a separate query (`p_threads_archived`). |

## Amendments made during implementation

The sketches above are kept as written; where the code differs, this list is the contract.

### Wire and disk types (`waku-protocol::orchestration`, #42, #43)

- **Casing.** Struct fields are `camelCase`. Every fieldless enum serializes as a `snake_case` string, which is also the value stored in indexed columns (`as_str()`); data-carrying unions use `"type"` with `snake_case` tags; `DomainEvent`, `Command` and `Effect` keep the dotted tags above. Capability groups keep RFC 0002's snake_case field names.
- **`DomainEvent` is internally tagged** (`{"type": "run.updated", ...entity}`), not adjacently tagged. serde's `#[serde(other)]` cannot skip the `payload` of an unknown adjacently tagged variant (decoding fails with "expected unit variant"), so adjacency would break R20. `thread.updated` becomes the newtype `ThreadUpdated(ThreadUpdate { change, thread })`. On disk nothing changes: `event_type` and `payload_json` (the entity, or `{change, thread}`) stay separate columns and `DomainEvent::from_parts` decodes the payload directly.
- **No reuse of the legacy `model` types.** `RuntimeMode`, `Attachment`, `PermissionOption`, `UserInputQuestion`/`UserInputOption`/`UserInputAnswer`, `ThreadGoal`/`ThreadGoalStatus` and `ContextUsage` are orchestration-native copies: the legacy enums reject unknown values and `MessageAttachment` has snake_case fields, which RFC 0003 §1.1 forbids. `orchestration::legacy` converts from the legacy types for #55 and #63. `NativeMetadata.resume_cursor` holds the legacy `ProviderResumeCursor` as `JsonText`, the opaque per-driver cursor (R23).
- **No `serde_json::Value`.** `DynamicTool.input`/`output` and `ContextRecord.data` are `JsonText` (RFC 0003 §1.1).
- **Fallbacks instead of `Unknown`** where a weakest value exists: `RefStrength`, `Quality` and `Enforcement` decode an unknown value to `None`/`None`/`ClientBoundary`; `NotificationSource` decodes an unknown source to `BackgroundTask` (the T3 rule stated above). Every other open enum and union ends in `Unknown`.
- `ContextHandoff.covered_run_ordinals` is `RunOrdinalRange { first, last }` instead of a tuple, so non-TS codegen gets a named type. `TransferResolution`'s handoff variants carry `handoff_id`.
- `TurnItem` gains `stream_rev: u32` (RFC 0003 §5.4), omitted when 0.
- `ContextRecord` is `{ context_id, kind, label?, data?: JsonText }`; its body stays opaque to the orchestrator.

### Commands and `decide` (`waku-orchestrator`, #39)

- **Derived indexes on `ThreadProjection`.** Besides the fields above it keeps `active_runs`, `queue` (queued runs keyed by `(queue_position, requested_at, run_id)`) and `max_ordinal`, all derived from `runs` (a load recomputes them, `apply` maintains them). `decide` therefore reads the active run, the queue head, the next queue position and the next ordinal without scanning the run history or the queue: deciding a dispatch against a thread with 1,000 queued runs takes about 0.8 µs.
- **Hot rows.** `hot_messages` and `hot_items` hold the rows of runs that are non-terminal or not (yet) known to the projection; rows outside a run are never hot. `apply` returns `ApplyOutcome { reload }`: when a terminal run becomes non-terminal again (`prepared_run.retry`), the cached projection is dropped and reloaded, because the rows that left the hot sets are only in SQLite.
- **Id allocation.** A run's id is UUIDv5 of its message id; its first attempt, root node, root checkpoint scope and user-message row derive from the run or message id; a checkpoint derives from `(scope, ordinal)`. New provider threads, event ids, and rows that can repeat for one run (interrupt results, error rows) take fresh ids from the `IdSource`, because a row's position is assigned once (R15) and must never move. A run takes an ordinal once: `start_run` ignores a run that already has one, and `prepared_run.retry` only applies to a run that failed before it took an ordinal (the property test found both cases).
- **Dispatch policy.** `Auto` starts an idle thread, steers a running turn only with native steering (`turns.active_steering`), and otherwise queues. `SteerActive` before the provider accepted the turn queues the message; without native steering it restarts the turn with a `steering_restart` attempt when the driver can interrupt. `RestartActive` needs a live provider turn. A held queue is detected by its head: holds and resumes always apply to the whole queue and new runs join at its end.
- `CapabilitySource` is `Send + Sync`. `CommandError` fields are owned strings (it is stored as `error_json`). `Effect::ProviderTurnInterrupt.subagent` is `SubagentTarget { node_id, native_task_id }` instead of a tuple.
- `PreparedRunProgress` persists nothing in Phase 2. `RecoverThread` and `ContinueRun` return `Unsupported` until #59, `ImportLegacyTranscript` until #63; `ImportLegacyThread` is implemented. Requests with a `Message` response capability are answered in Phase 3.

### Sink, storage and projections (#40, #42)

- **WAL checkpoints run off the commit path.** The writer sets `wal_autocheckpoint = 0`; a `Store`-owned checkpointer thread with its own connection runs `PRAGMA wal_checkpoint(PASSIVE)` at most every 100 ms while commits arrive and `TRUNCATE` on close. With `checkpoint_fullfsync = ON` (macOS) an automatic checkpoint inside a commit costs several milliseconds; measured on 10,000 streamed-text commits it was 2.4 s of 3.5 s.
- **Derived thread columns are maintained by deltas.** `queued_run_count` and `pending_request_count` change by the difference between a run's (request's) previous and new status, read from its row before the upsert; `activity` is re-derived with index lookups only when a status changes. A thread row inserted after its runs counts them once. Counting from scratch on every commit made a dispatch O(queue length). `waku doctor`'s verify recounts all three columns.
- **Provider-session bindings** come from the thread context of `provider_session.updated` events, not from `ProviderThread` rows, so loading a thread equals applying its events live. The session manager (#44) reports a session in every thread it serves.
- `CommitContext` gains `project_id` (thread events record their project for the shell stream). Event ids come from the shared `IdSource`. `CommitResult.events` are `Arc<StoredEvent>`, shared with feed subscribers without a per-subscriber clone, and a duplicate carries the stored `Receipt`. `commit_rejection` returns `Recorded(sequence)` or `Duplicate(receipt)`.
- `CommittedFeed` is bounded (16,384 events by default); a subscriber that falls behind is ended with `overflowed()` set and resubscribes from its cursor (RFC 0003 P9). Publishing happens after `COMMIT` while the writer is still held, so subscribers see commits in sequence order.
- `ingest` is split: `Orchestrator::ingest_decision(thread_id, Decision, WriteGuard)` is the post-decide half (lock, guarded commit, cache apply, wake), returning `Stale` when the guard fails. `decide_ingest`, `IngestEnvelope` and `AdapterEvent` arrive with #44.
- The `orchestrator_migrations.name` column holds the name without its numeric prefix (`init` for `0001_init.sql`).
- `projection::maintenance` provides `verify` (rebuild the log into an in-memory database in pages, compare every projection table row by row, check references and derived columns, and list outbox rows whose command has no accepted receipt), `rebuild` and `catch_up` (pages of 10,000 events, one transaction each, resumable). Superseding compaction (R3) is not implemented yet; events are kept, as R3 requires for Phase 2. `0002_search.sql` belongs to #65.

### Effect outbox and workers (#41)

- **`DefaultExecutor { provider: Arc<dyn EffectExecutor>, ports }`.** Until the `ProviderSessionManager` exists (#44), the provider side is an `EffectExecutor` that receives every provider-control effect: `provider_turn.*`, `runtime_request.respond`, `provider_session.detach`, and also `provider_thread.rollback` (the session manager rolls the conversation back, restores files through `CheckpointPort` when asked, and reports `CheckpointRollbackApplied` or `CheckpointRollbackFailed`), `provider_runtime.continue` (#59) and `delegated_tasks.stop` (P3). The ports run `workspace.prepare`, `checkpoint.capture`, `thread_title.generate` and the three cleanups. `EffectContext::report` dispatches an effect result and treats a rejection as "no longer applies" (settled), a storage error as retryable.
- **Shutdown is a crash.** `shutdown(grace)` stops claiming and waits up to `grace`; effects still running then get their cancel token signalled and their rows stay `running`, so the next start's `reconcile_after_process_loss` handles them (one recovery path, as above).
- Cancellation is cooperative: the worker re-reads the row after the claim (a cancel that raced it wins), signals the effect's `CancelToken`, and the executor polls or waits on it. A settle lands only while the worker still holds the lease, so a row cancelled mid-run stays `cancelled`.
- After every settle a worker wakes another one, so the next row of a blocked lane (or a retry's new due time) is picked up without waiting for the liveness poll. A row whose payload does not decode (an effect type from a newer version) settles `failed` and frees its lane.
- The liveness poll also prunes: succeeded and cancelled rows after `settled_retention` (7 days), receipts after `receipt_retention` (30 days), both in batches of `prune_batch`, then `PRAGMA incremental_vacuum(2048)`. Failed rows are kept.

### Search (#65)

- **Documents come from turn items, not messages.** `apply_sql` indexes a `user_message` item, an `assistant_message` item once it stops streaming, a `proposed_plan` item once it stops streaming, a `todo_list` item on every update (explanation plus step texts), and the thread title on every `thread.updated`. Items carry the text *and* the transcript position in one row; a message row has no position. `search_docs.entity_id` is still the message or plan id, so the RFC's columns hold. Queued messages become searchable when their run starts (their item is created then). Snippets are cut from the item at `(thread_id, position)` in `p_turn_items` (and from `p_threads.title`), not from `p_messages`/`p_plans`.
- **`search_docs.body_hash`** (FNV-1a of the indexed body) makes re-indexing an unchanged body a single index lookup. Every `thread.updated` re-checks the title, so without it each visit or activity commit would rewrite an FTS row. With it, `dispatch_commit/message_queue_10k` stays at 1.99 s and `text_snapshot_10k` at 1.38 s, as before #65.
- **`search_fts` has a second column, `thread`,** holding one token per document (`t<thread uuid hex>`). An in-thread find is `thread : "t…" AND body : (…)`, a doclist intersection; filtering a corpus-wide match by `search_docs.thread_id` costs a join per match.
- **Matching.** Each word of the query is a quoted prefix term and all must occur in `body` (`body : ("par"* "spa"*)`). A query with CJK/Hangul/kana characters, which `unicode61` does not split into words, falls back to a substring scan (`instr`) of the same documents' rows.
- **`SearchThreads`** (`search::search_threads`, `Orchestrator::search_threads`) returns one match per thread: the title, else the latest matching message, else the latest matching plan (one `GROUP BY` over the hits, no bm25), ordered by that source and then by `COALESCE(last_reply_at, updated_at)` descending; deleted threads are excluded and archived ones unless asked; an optional project filter. **`SearchThread`** (`search::find_in_thread`) returns every match position in the thread (capped at 5,000), the current match for an anchor position, and snippets for a window of ≤ 17 matches around it; `search::items_around` loads the rows at a match from `p_turn_items`, so a find jumps to history no client has paged in. These are Rust APIs on the read pool; the v8 stream methods expose them (#54).
- `GRAPH_SCHEMA_VERSION` is 2, so a database written before #65 rebuilds its projections, search included, on the next open. `rebuild` empties `search_docs` and `search_fts` (`'delete-all'`) with the projection tables, and `verify` compares `search_docs` row by row.
- **Numbers** (`benches/search.rs`, 10,000 threads in 10 projects, 105,001 documents, ~5.5 M words from a 4,000-word Zipf vocabulary; Apple Silicon, bench profile): search across threads, 50 results with snippets: rare word 0.42 ms, mid-frequency word 9.4 ms, two words 5.8 ms, the third most frequent word (matching nearly every thread) 35.7 ms, a two-letter prefix 39.9 ms. Find in a thread of 5,000 messages: 0.12–3.9 ms.

### Thread lifecycle (#64)

- **`lifecycle::LifecycleService`** is the auto-settle service and the snooze-wake scheduler in one thread. It subscribes to the committed feed, keeps at most two deadlines per thread in memory (`Scheduler`: the snooze end, and when the auto-settle rule must look again), and sleeps on `select!` over the feed, a control channel and the earliest deadline. Only `thread.updated`, `run.updated`, `runtime_request.updated` and `provider_thread.updated` events reload a thread, with one indexed query (`scheduler::load_facts`); startup reads every thread that can still settle or wake once. There is no periodic scan; the wait is capped at 10 minutes only to notice a wall-clock jump, and a capped wake-up reads nothing. A feed overflow resubscribes and reloads everything. `SnoozeWake` and `AutoSettle` carry derived command ids (`snooze-wake:<thread>:<at>`, `auto-settle:<thread>:<snapshot_at>`), so a repeated fire is a receipt hit.
- **The rule** (`lifecycle::policy::evaluate`, T3's `resolveAutoSettlementAt`): a candidate is not archived, deleted, settled, pinned, manually settled or unsettled (`settled_override` set), auto-settle-disabled, busy (a run preparing through finalizing, or queued runs), waiting on a request, holding provider background work, or snoozed (unless a run finished or failed after the snooze). A candidate settles at once when its pull request closed, or merged with `on_merge`, after the user's last message; with `keep_pull_requests` a thread with a pull request settles only that way; otherwise it settles `after_days` after its last activity (`last_reply_at`, run requests, starts and completions, a snooze wake). Settings are `AutoSettleSettings { defaults, projects: overrides }` with T3's defaults (3 days, merge on, keep off); the daemon passes them in (#55) and `set_settings` reschedules everything.
- **Pull requests** are not entities until the PR phase. The service reads them through `PullRequestSource` (answering from memory; `NoPullRequests` for Phase 2) and `pull_request_changed(thread_id)` re-evaluates a thread when a merge event arrives.
- `AutoSettle` in `decide` now refuses exactly what the rule refuses (it also checks archived, pinned, any `settled_override`, pending requests and background work) and is a no-op when the thread changed after `snapshot_at`. It sets `settled_at` only, so the user's override stays theirs, and closes the thread's terminals.
- **Re-engaging a settled thread.** `message.dispatch` on a settled thread clears `settled_at` and `settled_override` (`ThreadChange::Unsettled`): a new message brings the thread back to the active list, and auto-settle applies to it again.
