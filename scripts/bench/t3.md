# Running the baseline against T3 Code

Status: scripted, **not run yet**. The owner chose to measure Waku first (`docs/fork/bench/baseline.md`); this is the runbook for the T3 Code column of the same matrix (#9).

Measure both apps the same way, from outside, on the same machine, on AC power, with nothing else busy. `scripts/bench/harness.py measure` samples any process tree with the same counters the Waku runs use: `proc_pid_rusage` CPU (user+sys, including reaped children), interrupt wakeups, RSS and phys footprint. It splits the tree into the **shell** (the app, its helpers, its server) and the **provider CLIs** (`codex` / `claude`, real or fake), as PLAN §5.1 requires.

Paths below are relative to the Waku checkout. Facts about T3 marked *(check at the pin)* come from the audits in `docs/fork/audit/`, not from running T3; confirm them against T3 at `docs/fork/T3_PIN` before trusting a number.

## 0. One-time setup

1. Use T3 Code at the commit in `docs/fork/T3_PIN`. Build or install its **desktop** app (Electron), because Waku is a desktop app; `npx t3` in a browser adds a browser that is not part of the T3 process tree. Record the T3 version, its commit and the Electron version.
2. Build the fakes and the Waku tools:

   ```sh
   cargo build --release --locked -p waku-bench-daemon   # fake-codex, fake-claude, waku-bench-daemon
   ```

3. Pick a results directory and an isolated home. Nothing in it is the owner's real data:

   ```sh
   export T3B="$PWD/temp/bench/t3-$(date +%Y%m%d)"     # temp/ is gitignored
   mkdir -p "$T3B/home" "$T3B/results"
   export T3_EXE="/Applications/T3 Code.app/Contents/MacOS/<executable>"   # ls the bundle's MacOS dir
   ```

4. A bench project outside any git checkout (inside one, git and the file index see that repository):

   ```sh
   export T3_PROJECT="${TMPDIR:-/tmp}/t3-bench-project"
   mkdir -p "$T3_PROJECT" && echo '# Bench project' > "$T3_PROJECT/README.md"
   ```

## 1. Launch T3 isolated, with the fakes, and offline

For every launch:

```sh
export FAKE="$(scripts/bench/fake-path.sh --dir "$T3B/fake" --timeline prose --rate 1)"
env -i \
  HOME="$T3B/home" \
  T3CODE_HOME="$T3B/home/.t3" \
  CODEX_HOME="$T3B/home/.codex" \
  CLAUDE_CONFIG_DIR="$T3B/home/.claude" \
  T3CODE_TELEMETRY_ENABLED=false \
  PATH="$FAKE:/usr/bin:/bin:/usr/sbin:/sbin" \
  TMPDIR="$TMPDIR" USER="$USER" LANG=en_US.UTF-8 \
  "$T3_EXE" &
echo "T3 pid: $!"
```

- `T3CODE_HOME` moves T3's whole state directory (`~/.t3` by default, `apps/server/src/config.ts`) *(check at the pin)*. `HOME` covers Electron's own user data and anything T3 derives from the home directory.
- `CODEX_HOME` and `CLAUDE_CONFIG_DIR` keep the fakes, and any real CLI T3 might still find, away from real accounts. The fakes write nothing there, but T3 reads them.
- `T3CODE_TELEMETRY_ENABLED=false` turns off server-side analytics (`docs/user/telemetry.md`) *(check at the pin)*.
- **Provider update checks off.** In Settings, turn off `enableProviderUpdateChecks`. It gates the npm/brew version advisory; see `maintenanceResolver.ts` in `docs/fork/audit/t3-provider-adapters-detail.md` C2. Do it once in the isolated home before the first measured run. It persists under `T3CODE_HOME`.
- **Provider binaries.** T3 resolves `codex` and `claude` on its PATH. If it rebuilds PATH from a login shell, the isolated `HOME` has no shell rc files, so the fake directory stays first. If T3 offers a binary-path setting per provider instance, point it at `$FAKE/codex` and `$FAKE/claude`; that is more reliable. Confirm with `ps -o pid,comm -g <T3 pid>` during a turn that the provider children are `fake-codex` / `fake-claude`.
- **No network.** T3 also fetches a remote model manifest (`ModelManifest.ts`, "bundled, then remote fetch from main") *(check at the pin)*. Run with Wi-Fi off, or check during a run that only loopback sockets are open:

  ```sh
  lsof -nP -a -i -p "$(pgrep -d, -P <T3 pid>),<T3 pid>" | grep -v 127.0.0.1
  ```

  A run with any non-loopback connection is discarded.
- The fakes report an API-key account with no subscription, so T3 makes no usage-API call; see `crates/waku-bench-daemon/README.md`.

Find the root pid to measure. `measure` follows children, so the Electron main process covers the renderer, the GPU and utility helpers, the node server and its provider CLIs:

```sh
T3_PID=$(pgrep -f "$T3_EXE" | head -1)
```

## 2. Scenarios

Run each one 5 times (the issue asks for the median of 5; the committed Waku numbers used 3) and keep the JSON. `measure` prints the shell and the providers separately.

| Scenario | Timeline length (rate 1) |
| --- | --- |
| `prose` | 200 s |
| `burst` | 10 s |
| `reasoning-fast` | about 12 s |
| `code-wall` | see `target/release/waku-bench-daemon list` |
| `tool-storm` | about 30 s (300 calls × 100 ms) |

### Idle

Launch as in §1 with the bench project open and three short threads, the composer **not** focused, the window visible. Wait 10 s, then:

```sh
python3 scripts/bench/harness.py measure --pid "$T3_PID" --seconds 50 \
  --label t3-idle --json "$T3B/results/idle-r1.json"
```

Waku's matching row is `idle` (60 s open, measured over the last 50 s).

### Streaming: `prose`, `burst`, `reasoning-fast`, `code-wall`, `tool-storm`

For each timeline and each provider (Codex, then Claude):

1. Launch as in §1. Open a new thread in the bench project with the provider selected.
2. Type the timeline's name as the whole prompt, for example `burst`. The fakes replay the timeline named by the prompt.
3. Start the sampler, then press Return within a second:

   ```sh
   python3 scripts/bench/harness.py measure --pid "$T3_PID" --seconds <length + 5> \
     --label t3-burst-codex --json "$T3B/results/burst-codex-r1.json"
   ```

4. Quit T3 (cmd-Q) before the next run, so every run starts from the same state.

Compare `shell.cpu_pct` with Waku's **app + daemon** CPU for the same timeline. The Waku baseline drives `waku-bench-daemon`, which has no provider process. For a like-for-like run with the provider CLIs in the loop, run Waku the same way: launch `target/release/waku` without `WAKU_DAEMON_ADDRESS`, so it spawns the real `waku-daemon`. Use the same `env -i` block with `HOME` pointed at a Waku-specific directory, set the Codex and Claude binary overrides in Waku's settings to `$FAKE/codex` / `$FAKE/claude`, and measure Waku's pid with the same command. `providers.*` should then match between the two apps.

The visual update rate matters as much as CPU (PLAN §5.1 compares CPU **at** a higher update rate). Waku reports its commits and frames per second from perf counters. For T3, record the Animation Hitches trace from §3 during one run per timeline.

### Memory with N long threads (1, 5, 20)

T3 has no bench seeder. Waku's rows use 2,000-message sessions seeded straight into its database, then visit each one. The closest manual equivalent:

1. For N = 1, 5, 20: create N threads in the bench project and, in each, run `prose` with `--loops 5` (`scripts/bench/fake-path.sh --timeline prose --loops 5 --rate max`, prompt `prose`). Five loops give each thread one long turn of 100k tokens. That is long, but it is not 2,000 messages, so the rows are **not** directly comparable to Waku's. Label them as such.
2. Visit each thread once, wait 20 s, then `measure --seconds 5`. Report `shell.footprint_final_mb` and `shell.footprint_peak_mb`.

Seeding T3's own database with 2,000-message threads (SQLite under `T3CODE_HOME`) would make this exact. It is not written yet; see the gaps in `docs/fork/bench/baseline.md`.

### Cold and warm start

The Waku rows come from Waku's own counters (process start → first frame / first transcript row). T3 has no such counter. Use the same external tool for both apps:

```sh
xcrun xctrace record --template 'App Launch' --output "$T3B/results/launch-r1.trace" \
  --launch -- "$T3_EXE"
```

Run it with the §1 environment exported first. Read the time to first frame from the trace. Cold is the first launch after installing or building; warm is any repeat. A true cold launch needs `sudo purge`, which this harness avoids. Record the Waku launch with the same template (`--launch -- target/release/waku`, with `WAKU_DAEMON_ADDRESS` / `WAKU_DAEMON_TOKEN` for a running `waku-bench-daemon`), so the two columns use one method.

### RPC latency

Not applicable: T3's client and server latency is internal to T3. Waku's row is `rpc-latency` against `waku-daemon`.

## 3. Frame pacing (both apps)

Not scripted yet; this is the issue's frame-time p99 row. Per app, record one streaming `prose` run and one scroll through a long thread with the Animation Hitches template:

```sh
xcrun xctrace record --template 'Animation Hitches' --attach <pid> --time-limit 60s \
  --output "$T3B/results/hitches-prose.trace"
```

Report the hitch-time ratio (ms of hitches per second) and frames over 8.33 ms at 120 Hz.
